# Сборка и публикация ArenaMP

[English](BUILDING.md) · [Проект](../README_RU.md)

## Платформы и состав

| Платформа | Среда сборки | Результат |
|---|---|---|
| Windows x64 | Visual Studio 2022, Ninja, `windows-2022` | ZIP: лаунчер, обновлятор, клиент, сервер и ресурсы |
| Linux x86_64 / Steam Deck | Ubuntu 22.04, GCC, Ninja | Переносимый `.tar.gz` с обёртками запуска и библиотеками |

Используется конфигурация Release и Rubic0n LuaJIT из `extern/LuaJIT`. Для загрузки инструментов и внешних зависимостей нужен Интернет. Данные Morrowind предоставляются отдельно.

## Подготовка репозитория

Скопируйте **содержимое** папки `ArenaMP/` в корень GitHub-репозитория. На одном уровне должны находиться `CMakeLists.txt`, `apps/`, `components/`, `server/`, `extern/` и `.github/`. Не создавайте лишнюю вложенную папку ArenaMP. Сохраните служебную папку Git своей рабочей копии.

```bash
git add -A
python3 CI/verify-rubic0n-vendor.py
git commit -m "Prepare ArenaMP first public release"
git push origin main
```

Укажите реальную ветку своего репозитория. Проверка LuaJIT читает индекс Git, поэтому её запускают после `git add`. Файл `src/luajit.h` создаётся при компиляции; его отсутствие в несобранном дереве нормально.

## Автоматическая сборка и выпуск

[Workflow](../.github/workflows/release-builds.yml) запускается при отправке коммита в `main`/`master`, отправке тега `v*` и вручную. Для ручного запуска откройте **Actions → Build and release (Windows, Linux) → Run workflow**.

| Параметр | По умолчанию | Назначение |
|---|---|---|
| `build_windows` | Включён | Windows x64 |
| `build_linux` | Включён | Linux x86_64 / Steam Deck |
| `clear_build_cache` | Выключен | Не использовать сохранённые скомпилированные кеши |
| `publish_release` | Выключен | Опубликовать успешные пакеты во вкладке **Releases** |
| `release_tag` | Пусто | Имя тега при ручном выпуске, либо автоматически по номеру запуска |

Отправка коммита или тега запускает обе платформы. Вручную можно выбрать одну или обе. Если обе отключены, выпуск не создаётся. При очистке кешей сборки загрузочные кеши зависимостей могут сохраняться.

Обычные коммиты в `main`/`master` и ручные запуски без опции `publish_release` дают **только артефакты Actions**. Публикация во вкладке **Releases** выполняется, когда отмечен `publish_release` или отправлен тег `v*`. Все выбранные задачи должны пройти сборку, проверки и упаковку. Ошибка или отмена хотя бы одной выбранной платформы блокирует выпуск. Отключённая платформа может быть пропущена.

В настройках репозитория включите Actions. Политика репозитория или организации должна разрешать задаче публикации запись содержимого репозитория. Workflow запрашивает `contents: write` только для публикации и использует штатный `GITHUB_TOKEN`; отдельный персональный токен не требуется. Если политика запрещает запись, готовые пакеты останутся в Artifacts, а создание Release завершится ошибкой.

## Что появляется в Releases

- ZIP Windows и/или переносимый архив Linux — согласно выбору платформ.
- `ArenaMP-Source-<номер>-<попытка>.tar.gz` — исходники репозитория на коммите сборки.
- `BUILD_INFO.json` — коммит, запуск и состав платформ.
- `SHA256SUMS.txt` — контрольные суммы файлов выпуска.

Имена бинарных пакетов также содержат номер запуска и попытки. Диагностические журналы остаются во вкладке Actions. Архив исходников содержит отслеживаемые скрипты и уведомления; загружаемые во время сборки инструменты и зависимости описаны в workflow и реестре зависимостей.

Для тега `v*` используется его имя. В остальных случаях создаётся `build-<номер>-<попытка>`. Публикация запускается после подготовки и проверки всех выбранных пакетов; неуспешная сборка блокирует общий выпуск. Для нового выпуска используйте новый тег.

Пример собственного номера выпуска:

```bash
git tag v1.0.0
git push origin v1.0.0
```

Это пример имени тега; он не меняет протокол или внутреннюю версию движка. Каждый push в наблюдаемую ветку запускает отдельную сборку, но для обычного коммита без тега автоматической публикации в Releases нет.

## Локальная сборка

Команды и требования приведены в [английском руководстве](BUILDING.md#windows-local-build). Для Windows нужна совместимая с CI среда Visual Studio/MSYS. Для Linux используется Ubuntu 22.04; сначала собирается Rubic0n LuaJIT, затем его заголовки и библиотека явно передаются CMake. Результат локальной упаковки Linux находится в `artifacts/`.

Полная последовательность установки зависимостей и проверки пакетов находится в workflow. Не переносите только EXE: лаунчеру, обновлятору, агентам и серверу нужны комплектные библиотеки, скрипты и ресурсы.

## Проверка выпуска

Проверьте контрольные суммы, запуск лаунчера и своего сервера, соединение двух клиентов, переходы между ячейками, сохранность жилья, голос и восстановление соединения. Рабочие данные сервера не должны попадать в исходный репозиторий. См. [проверки](guide/VALIDATION.md) и [происхождение зависимостей](guide/DEPENDENCY_PROVENANCE.md).

Выпуск в GitHub Releases и обновления из лаунчера настраиваются отдельно. Для игровых обновлений нужны URL и манифесты — [руководство обновлятора](arena-updater/README_RU.md).

## Rubic0n LuaJIT и OpenSSL только Release

Полный каталог `extern/LuaJIT` должен содержать настоящие `src/Makefile`, `src/luajit_rolling.h` и другие исходные файлы. Файл `src/luajit.h` **создаётся при сборке**. После `git add -A` запускайте `python3 CI/verify-rubic0n-vendor.py`: проверка обнаружит исходники, проигнорированные Git. На обычный LuaJIT возвращаться не требуется.

Для Windows OpenSSL использует `CI/vcpkg-triplets/x64-windows-release.cmake` с `VCPKG_BUILD_TYPE=release`: библиотека устанавливается в `C:/vcpkg/installed/x64-windows-release`, **без отдельной компиляции Debug-варианта**. Это не отменяет библиотеки совместимости TLS для Qt 5.
